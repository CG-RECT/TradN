# TradN 参考项目与演进建议

> 调研时间：2026-09-20。项目状态和许可证可能变化，实际借用代码前必须再次核对对应仓库的最新许可证。

## 1. 结论

现有开源项目通常只覆盖交易日志、投资组合、行情数据或策略回测中的一部分。TradN 的差异化方向是把“市场事件和走势观察、交易规则执行、真实交易、主观预测、亏损复盘、规律验证”连接成一个长期闭环。因此不建议整体替换为某个现成项目，更适合借鉴成熟的数据口径、交互和分析方法。

## 3. 建议的功能演进顺序

### 第一阶段：把复盘数据变得可统计

1. 为交易增加“策略/形态、错误类型、情绪、规则遵守情况、截图、复盘结论”等结构化字段。
2. 把开平仓规则升级为可版本化的规则模板，保存每笔交易实际使用的模板版本。
3. 增加规则遵守率、违反规则后的盈亏、连续亏损、期望值、盈亏比和按时间段统计。
4. 建立亏损归因库，同一种错误可以关联多笔交易，并展示是否重复发生。

### 第二阶段：建立事件、判断和结果闭环

1. 新增市场事件模块，记录事件时间、类别、重要性、预期、实际值、来源和受影响品种。
2. 新增交易假设/走势预测模块，记录方向、目标区间、有效期、置信度、依据和失效条件。
3. 到期后人工或自动标记预测结果，统计不同依据、时间周期和置信度的命中率。
4. 时间线中的事件、预测、交易和笔记使用明确关系表互相关联，而不仅依赖标签。

### 第三阶段：支持多品种

1. 引入统一的 `instrument`（标的/品种）概念，至少包含市场、代码、名称、品种类型、计价币种和时区。
2. 交易、时间线、事件、预测、规则模板和笔记逐步关联 `instrument_id`。
3. 黄金专属问题保留在黄金规则模板中，通用交易表不写死黄金字段。
4. 页面默认仍选择黄金，避免为未来扩展牺牲当前使用效率。

### 第四阶段：数据接入和验证

1. 用独立 Provider 接口接入行情、经济日历、新闻和持仓/资金数据，保存来源、抓取时间和原始标识。
2. 外部数据接入与 TradN 核心业务解耦；必要时使用独立 Python 数据服务，通过 REST 或消息任务同步。
3. 在积累足够样本前，不使用复杂 AI 给出确定性买卖结论；先做检索、归纳、反例提示和统计验证。
4. 当规则能明确表达为计算条件后，再考虑回测，并显式处理手续费、滑点、未来函数和样本外验证。

## 4. 当前最值得优先实现的三个能力

1. **规则/错误与盈亏关联分析**：最直接服务“避免重复踩坑”，也是现有交易记录和问卷数据最容易形成价值的方向。
2. **事件与走势假设模块**：把“哪些事件可能影响接下来走势”从自由文本升级为可跟踪、可验证的数据。
3. **多品种基础模型**：先建立 `instrument` 边界和接口，不必立即改完所有页面，但避免新功能继续把黄金写死。

## 5. 借鉴开源项目时的约束

- 优先借鉴信息架构、统计指标和交互，不直接复制未知来源或许可证不兼容的代码。
- 引入第三方代码必须记录仓库、版本、许可证和修改内容。
- 外部项目的数据结构不能直接决定 TradN 的业务模型，应以 `产品愿景与长期原则.md` 中的目标为判断标准。
- 对预测、AI 分析和市场规律必须同时展示依据、样本范围和反例，避免形成不可验证的“黑箱结论”。
